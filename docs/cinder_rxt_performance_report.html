Tier 1: Executive Adoption Brief

1. High-Level Summary & Value Proposition

OpenStack block storage clusters operating on standard LVM drivers face two critical operational liabilities: 1. Critical Data Corruption / GPT Truncation (OSPC-2358): Standard LVM volume copies format LUKS headers directly into unpadded Logical Volumes, lopping off 4 MiB at the device tail. Boot-from-Volume (BFV) instances boot with corrupted backup GPT partition tables, broken filesystems, or non-bootable emergency shells. 2. Cluster I/O Freezes & Host Exhaustion: Legacy LVM snapshots instantiate kernel Copy-on-Write (COW) LVs inside the host Volume Group. Long-running snapshots degrade disk read/write throughput by over 80%, pin single CPU cores during single-threaded dd copies (causing 96%+ physical disk saturation), and risk total Volume Group exhaustion when snapshots fill up.

The cinder-rxt driver resolves both issues at the architectural root: - Automatic 4 MiB LUKS Alignment Padding: Every encrypted volume LV is automatically provisioned with a 4 MiB buffer (+4 MiB), ensuring secondary GPT headers land precisely within block boundaries with zero corruption. - Offloaded Differential Snapshots to Swift: Host LVM COW snapshots are purely transient (<1 second). Payload chunks (4 MiB) are scanned in parallel across all 32 host CPU cores at ~1,000 MB/s and streamed directly to Swift object storage. No COW LVs remain on the host volume group. - Massive Parallelism: Replacing single-threaded Python/dd with a multi-threaded Rust worker (cinder-rxt-worker) that distributes hashing, compression, and network transport across all 32 CPU cores without saturating physical disks or incurring iowait.

2. Snapshot Architecture Deep-Dive: Scan Phase Rationale & Pipelining

During Step 4 testing, differential snapshot creation exhibited two distinct phases: - Phase 1 (Parallel Scan): 42.2 seconds (970.3 MB/s across 32 CPU cores) - Phase 2 (Swift Streaming): 188 seconds (218.1 MB/s upload)

Why Does the First Snapshot Require a Scan?

Even on the very first snapshot of a volume, Phase 1 performs two essential functions: 1. Sparse / Zero-Block Pruning (block_io::is_all_zeros): Unwritten or zeroed 4 MiB chunks are pruned during scanning and marked as None in the manifest. They are never uploaded to Swift. For partially populated or sparse volumes (e.g., an unencrypted 40 GiB volume with 5 GiB of filesystem data), this avoids uploading tens of gigabytes of zeros over the network. (Note: For LUKS-encrypted volumes, ciphertext fills the allocated sectors, resulting in all 10,241 chunks being active). 2. Content-Addressable Hashing (compute_chunk_hash): cinder-rxt-worker computes SHA-256 chunk hashes to generate content-addressable object keys (chunks/<hash>) in Swift and construct the initial manifest (block_map). This manifest serves as the baseline for all future differential snapshots.

Architectural Optimization: Concurrent Scan & Upload Pipelining (Implemented & Certified)

In the initial baseline implementation, Phase 1 (Scanning) and Phase 2 (Uploading) executed serially. This introduced two major latency bottlenecks: 1. Serial Waiting: Swift upload was idle for the first ~42 seconds while the entire disk was scanned. 2. Double Read from Disk: The scanner read disk blocks to compute hashes and discarded the buffers. The uploader then re-read the exact same blocks from disk a second time. 3. Redundant HTTP HEAD Requests: For initial snapshots or new volumes, the uploader made up to 10,241 individual HTTP HEAD calls to Swift to check object existence, adding unnecessary round-trip overhead.

Optimized Pipelined Architecture: - Producer-Consumer Tokio MPSC Channel: Implemented a bounded channel (tokio::sync::mpsc::channel) with automatic backpressure. Scan tasks read chunk data into memory buffers once, compute SHA-256 hashes, and stream dirty chunk buffers directly to the upload pool. - Zero Double Reads: Block data is read from disk exactly once. Data buffers are transferred directly from the scan thread to the Swift put_object pipeline. - Zero HTTP HEAD Calls on Baselines: Because new volumes have no prior Swift objects, HTTP HEAD checks are bypassed completely. An in-memory HashSet<[u8; 32]> tracks uploaded chunks to eliminate identical blocks in real time. - Strict Memory Safety & Dynamic RAM Auto-Sizing: The MPSC queue depth is fully configurable via --max-buffer-mib (and rxt_snapshot_buffer_mib in cinder.conf). If unset or set to 0, the worker dynamically inspects host available RAM via /proc/meminfo and safely allocates up to 1/16th of available memory, clamped between 256 MiB and 2048 MiB (e.g., 512 chunks = 2,048 MiB on block04 with 111 GiB available RAM). This bursts absorption of fast disk reads without stalling network uploads. - Progress Reporting: Integrated smooth, monotonic PROGRESS: <pct>% telemetry combining scan progress and upload progress across Tokio tasks.

2. Resolution of OSPC-2358: Verification & Proof

The Problem: Legacy LUKS Truncation

When standard LVM formats LUKS encryption on a 40 GiB Logical Volume (40960 MiB = 83,886,080 sectors of 512 bytes), the LUKS2 header consumes 4 MiB (8,192 sectors). The usable encrypted container is reduced to 83,877,888 sectors. When an unencrypted image is copied into this container without adjusting the LV size, the secondary (backup) GPT partition header—positioned by cloud image builders at the disk tail (LBA -1)—is written beyond the physical boundaries or truncated.

Console logs from the legacy node (block01) confirmed severe GPT corruption:

[ 3.667691] virtio_blk: [vda] 83881984 512-byte logical blocks (42.9 GB/40.0 GiB)
[ 3.678038] GPT:Primary header thinks Alt. header is not at the end of the disk.
[ 3.681175] GPT:7340031 != 83881983
[ 3.682571] GPT:Alternate GPT header not at the end of the disk.
[ 3.686516] GPT: Use GNU Parted to correct GPT errors.

The Solution: cinder-rxt 4 MiB Alignment Padding

cinder-rxt inspects volume encryption metadata during allocation. If the volume is encrypted, it provisions 40964 MiB (+4 MiB):

  • LV size verified via sudo lvs --units m: 40964.00m
  • Usable block device after LUKS header: Exactly 83,886,080 sectors (40.000 GiB usable payload).
  • Secondary GPT header lands safely inside device bounds. Zero kernel warnings, zero filesystem errors.
  • Test instance rxt-bfv-vm-test (651b54df-0e46-453a-bcca-20c0e278b7ed) booted directly from the encrypted volume: completed cloud-init, generated SSH host keys, and cleanly presented ubuntu login:.

Volume & Swift Container Teardown (TC-08)

  • Deletion of snapshots invokes cinder-rxt-worker delete-snapshot with --concurrency 32.
  • When the final snapshot for a volume is deleted, cinder-rxt automatically purges the Swift container (cinder-snapshots-<vol_id>), eliminating orphan object storage leaks.
